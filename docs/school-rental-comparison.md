# 学区別の募集比較一覧

## 確定条件（2026-09-23）

- 文京区、賃料17万5,000円以上（管理費等を含めない）、48㎡以上。マンション等は専有・使用部分面積、戸建は建物面積。
- REINS、ITANJI、いい生活、ATBBの広告可を確認した募集を対象にする。要連絡・条件付き許可は一覧から除外する。
- ITANJI、いい生活、ATBBは申込なしの画面上の根拠を保存する。ITANJIの申込数はユーザー確認済みの画面仕様に従い、空欄（数値表示なし）を申込なしと扱う。画面が取得できない状態とは区別する。
- REINSは在庫一覧と広告転載区分を確認。申込あり・募集終了の明示があれば除外する。
- 一覧はAD・24時間以内の更新条件を要求しない。AD条件を満たす物件の写真付き個別掲載は既存の取込・公開審査を利用する。
- ADの「迄相談」は確約ではない。社内の候補欄で区別し、一般向けの一覧、HTML、構造化データには出さない。
- ATBBは「広告転載可能な他サイト：客付不動産会社HP」を確認する。「アットホーム媒体」の転載可・要確認・不可とは別区分なので、自社HPの許可を独立して判定する。追加条件に承諾書送付・連絡等が必要なら除外。業者間閲覧可だけでは許可としない。自動取得アダプターは未実装。

## 画面と保存

`/gakku/rentals` に全体の比較一覧、`/gakku/{school}/rentals` に学区別の一覧を表示する。住所から小学校を確定できない物件は、全体・学校別とも掲載しない。学校別ページでは写真付きの既存物件カードの下に比較一覧を置き、件数は合算する。UIは4言語、原文の固有名詞・契約条件は日本語原文であることを明示する。

`/admin/bukken/school-rentals` で取得元単位のJSONをチェック・反映する。`school_rental_feeds` はPrisma経由のサーバー専用テーブル。Data APIに公開せず、RLSを有効にする。公開画面に渡す値は明示的なスキーマで限定する。

既存物件の内部の建物・住所・号室と照合し、下書き・募集終了を含めた登録済み号室を重複登録しない。同じ建物・住所・号室は取得元をまたいで1件にする。名称や号室を特定できない場合は無理に統合しない。最新確認の条件を採用し、別サイトの新鮮な募集終了・申込ありは優先して除外する。

学区は既存の文京区公式区域データと住所で判定する。番・号不足や区域境界は推定せず、学区を確定できなければ掲載しない。管理費・共益費の空欄はゼロとせず、合計も未確認と表示する。毎週水曜日12:00（日本時間）に募集情報を更新する。確認から26時間で非表示にする処理は廃止し、経過時間だけで掲載を終了しない。確認日時と次回更新予定は表示する。未確認条件を「可」に変換しない。

## 更新手順

1. 全ページを確認し、取得元ごとに `RentalFeed` 形式のデータを作る。`scope` は `bunkyo-rent-175000-area-48`、`complete` は全件確認時のみ `true`。`expectedCount` は検索画面で確認した全登録ID数（検索分割の境界で重複した同じIDは1回）であり、広告可だけの数ではない。取得件数と一致しないJSON、expectedCount未指定の新規書込みは拒否する。保存済みの旧形式は引き続き読める。各種条件、広告許可原文、申込状態の根拠、確認日時を保存する。
2. REINSの500件制限に注意し、必要なら重複しない賃料帯・種別で検索を分ける。境界の包含で重複した登録IDを統合し、検索総件数と取得件数を照合する。
3. 管理画面で登録前チェックを実行し、掲載件数・除外理由・AD候補を確認する。
4. 「学区別一覧に反映」で取得元の前回データを原子的に置き換える。今回の完全な検索結果に含まれない募集は、その取得元の一覧から消える。他の取得元の最新確認は維持する。同時更新や古いデータの上書きは拒否する。
5. ログイン失敗・途中取得を空の完全結果として保存しない。確認が間に合わない場合は確認日時を維持し、確認未了を運用者へ報告する。取得失敗を募集終了として一括削除しない。

管理画面の保存はビルド不要。学区ルートは既存の `force-dynamic` を維持し、全学校×全言語の静的生成を追加しない。

## 件数の定義

- 取得元の登録数と公開物件数は異なる。全取得元の登録数＝比較一覧の採用数＋除外登録数。除外理由は最初に該当する理由を1つだけ付けるため、同じ登録を複数の除外理由に重ねて集計しない。
- 管理画面の比較一覧件数は全providerを反映した残高であり、今回の新規追加数ではない。AD候補はその内数であり、加算しない。
- 学区ページの賃貸件数＝その言語・確認時点で実際に表示する写真付き公開物件数＋当該学区の比較一覧件数。既存物件との同一号室は比較一覧から除外する。日本語限定の個別物件があれば他言語の件数と差が出る。
- 状態がpublishedでも、個別賃貸の確認期限・言語条件・学区条件により公開されない場合がある。DBのpublished行数だけを公開件数としない。
- 見出し・学区選択の件数・一覧の行数・学区物件ItemListは同じ公開対象から作る。ハブのItemListの20件は学校数であり物件数ではない。

## 売買追加時の集計仕様（売買学区機能の実装時に適用）

売買もREINS・ITANJI・いい生活・ATBBを対象とする。各サイトで賃貸の後に売買を確認し、サイト横断で同一販売単位を照合してから既存propertiesへ物件ごとに一度保存する。賃貸フィードには混在させない。売買検索の提供・契約権限は各接続先で確認し、未対応・未取得は0件としない。自社HP広告可の証拠は取得元ごとに保持する。価格・面積・広告条件・販売状態の不一致は根拠を照合して解決し、後勝ち上書きや1媒体消失だけでの一括終了を行わない。

- 学区別表示は「賃貸N件／売買M件」、売買内訳は「マンションA件・戸建てB件・売地C件」。M=A+B+C。売買に「募集中」を流用せず「売出中」を使う。
- 区分マンションは独立した販売条件の1戸、戸建ては独立販売する1棟、売地は独立販売する1区画を1件とする。同じ販売単位の重複登録・写真・図面・言語版・学区ページと取扱物件ページの両表示を加算しない。
- 複数筆の土地を一括価格で売る場合は1件。区画ごとの価格・条件で個別販売する場合は区画ごとに1件。資料中の全区画数だけで販売中件数を増やさない。同一販売単位を確認できなければ保留する。
- 同一号室が賃貸と売買に出る場合は取引が異なるため各区分に1件ずつ計上する。合計表示するなら「掲載情報N件」とし、建物・世帯の実数と呼ばない。
- 一覧のカード、見出し、種別フィルター、ページ送り、構造化データは同じ重複除外・公開判定済みの集合から計算する。ページ送り時は総件数と当該ページの表示件数を区別する。画像がない物件も公開条件を満たして表示されれば1件であり、画像枚数では算定しない。
- 更新レポートは新規公開・継続公開・再公開・非公開化・条件変更・保留を区別。新規/再公開/非公開化は公開集合の前後差分で数え、条件変更は継続公開の内数とする。非公開化を成約と推測しない。
- 売買学区機能のテストに、重複REINS登録、異なる号室、複数筆一括売地、独立販売区画、賃貸売買両方の号室、下書き・終了・学区未確定、4言語の公開可否、フィルターとページ送りの総数一致を含める。
- 「平均2倍以上」は物件集合の足し算とは異なる営業実績の指標。検索総数÷広告可件数から自動算出せず、賃貸の案内文を根拠なく売買へ流用しない。

## REINSのローカル変換

認証・ブラウザー操作はこのスクリプトに持たせない。ブラウザーで取得した全文スナップショットを次のマニフェストに保存する。原本や取込JSONは機密を含むためGitへコミットしない。

```json
{ "scope": "bunkyo-rent-175000-area-48", "complete": true, "expectedCount": 513, "snapshots": ["取得した各詳細画面の全文"] }
```

513は2026-09-23の件数確認値（マンション等486＋戸建27）であり固定値ではない。毎回の検索総件数を使う。広告可・重複等の確認前の件数。

```sh
node --import tsx scripts/rental-import/reins-school-feed.ts capture.json 確認日時ISO feed.json
```

出力には確認した全登録を内部用として保存する。公開射影で広告可のみに限定し、募集終了・申込ありの根拠は他サイトの同号室の除外にも使う。空欄と次のフィールド名を取り違えず、全角のAD数値を正規化する。取得件数不一致・重複登録IDは停止する。確認日時は実際の確認時刻（複数ページの場合は最も古い時刻）を使い、再変換で更新しない。

2026-09-23 15:23以降の新条件全513登録を詳細画面で確認。広告可189登録、要連絡106登録、不可215登録、媒体限定の一部可3登録。広告可から既存掲載2登録・同一号室19登録を除く168件を整理した（学区確定161件・学区要確認7件）。AD記載候補20件は全て「迄相談」で、支払い確約ではない。広告可判定とAD条件の相談は別に扱う。重複登録にだけAD記載がある場合も、社内候補に証拠を残す。

取得時は物件番号だけでなく「広告転載区分」が現れるまで詳細画面への遷移を待つ。一覧にも同じ物件番号があるため、番号だけの待機では先頭登録の詳細取得に失敗する。全登録IDと検索一覧の順番・件数を最後に照合する。旧20万円・55㎡のデータを新条件の完全結果として使わない。

## 初回反映

コードのレビュー・マージ後に、Prismaの追加マイグレーションを通常の管理手順で適用する。マイグレーション未適用時は既存の物件カードを維持し、比較一覧は空になる。本番スキーマ変更と本番データ投入は今回のコード検証には含めない。

ATBBの確認資料： https://business.athome.jp/service/atbb/ （2026-09-23確認）。転載可・要確認・転載不可の区分と2次広告の説明。自社独自サイトへのデータ自動連携は別途確認する。

一覧の問い合わせは既存の内見CTAを1件ずつ開く。氏名、契約主体、入居人数、外国籍の場合の在留資格、ペットの種類・頭数、希望日程を収集し、メールと電話を両方必須にする。

## ATBB実査（2026-09-23）

同じ地域・賃料・面積条件で427登録。アットホーム媒体区分は転載可203、要確認62、転載不可162。この区分だけで自社HP掲載を判定しない。「客付不動産会社HP」フィルターで50登録、同一号室を整理して41件。詳細42登録を確認し、うち1登録は広告掲載承諾書が必要で除外。詳細確認済みで重複・要手続を除いた許可候補は32件。

残り8登録は契約検索枠100件への到達により詳細未取得。課金プランは変更していない。不完全なのでATBBの完全フィードとして保存しない。全体一覧には申込あり13登録、HP抽出50登録には申込あり表示なし。ただしATBBで記載なしを申込なしと確定する根拠は未確認で、公開候補への自動昇格は行わない。ITANJIで確認済みの空欄ルールを他サイトへ流用しない。

ATBBの賃料・物件番号は画像として表示されるため、DOMの空値をゼロにしない。取得済み表示を目視確認し、未取得分は未確認とする。詳細ページ閲覧も契約枠を消費し得るため、開始時と途中で利用状況を確認する。上限画面が出たら止め、月額変更を無断で承認しない。
