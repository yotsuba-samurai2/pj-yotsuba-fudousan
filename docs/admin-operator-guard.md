# F-001 管理API認可の独立修正案

base: bfa76e06127907f7c2ed25c19ff22cce9faa8918。ローカル修正・試験のみ。本番未適用。

Supabaseが返した確認済みメールを、サーバー専用 `ADMIN_OPERATOR_EMAILS`（カンマ区切り）と比較する。未許可・未確認は403、設定不足は503、セッション不正は401。`user_metadata` は使わない。既存routeの認証関数signatureは維持する。inquiriesの所有者限定は別のまま。

この変数を未設定でデプロイすると管理操作は503になる。初期operatorは所有者指定により `uramatsujoji@luck428.com` 1名に確定。設定予定値は `ADMIN_OPERATOR_EMAILS=uramatsujoji@luck428.com`（サーバー専用）。2026-10-23 JST、既存 Auth に一致アカウント1件・メール確認済み1件を件数のみのSELECTで確認した。実ログインの確認とは区別する。

適用前に Preview にこの許可リストを設定して、許可operatorのログイン・GET成功と未許可アカウントの拒否を確認する。テストアカウント用の別アドレスを本番へコピーしない。

1. 修正ブランチの Preview が今回のcommitであることを確認する。
2. Preview の設定とデプロイを揃え、未ログイン401、許可されていない利用者403、指定管理者200を確認する。拒否テストは隔離したテスト認証環境で行い、本番に利用者を新規作成しない。
3. 本番適用承認後、同じサーバー専用設定を本番に用意し、修正版を適用する。メール以外の秘密情報を移送しない。
4. 適用後は指定管理者の読取りと未ログイン拒否を確認する。権限のない利用者も通す旧コードへ安易に戻さず、不具合時も許可リストによる制限を維持する。

本番環境変数、signup設定、利用者、権限、DB、掲載は変更していない。コードの本番適用と設定値は別途承認が必要。Signupを無効にするだけでは既存の認証済み利用者への過剰権限は解消しない。

試験はSupabase/getUser・物件DBをmockし、実セッション作成・本番API呼出しは行わない。GET/POST/PATCH/DELETEで未許可利用者がDBへ到達しないことを確認する。
