# 読取り再試行の提案契約（実行なし）

`read-retry.ts` はRF01〜04/27/28に対応するローカルの純粋関数。通信、待機、SDK呼出、ブラウザ再操作、資格情報更新をしない。出力は常に`executable:false`であり、再試行を実行できた/実APIで回復したとは扱わない。

## 対象と停止

source/account/operation/HTTP method/host参照/正規化path/endpoint契約hashを設定版に固定する。先頭/途中の二重slash、dot/encoded/query等をpathに許容しない。将来のreaderではURL組立後にも承認originとの一致を確認する必要がある。GETだけではread-onlyと認定せず、明示的な読取り確認と許可参照が必要。実連携の確認が済んでいない媒体には承認値を埋めない。REINSはこの自動化契約の対象外。

認証・権限・CAPTCHA・証明書エラー・redirectを最優先で停止し、Retry-Afterやrateラベルで上書きしない。403は確認済みrate制限根拠がある場合だけ提案。未確認分類、一般403、不正Retry-After、その他不明エラーを再試行扱いしない。TLS検証無効化/redirect先への許可継承は不可。

## 単一予算・履歴

- 初回を含む総試行回数を設定。SDKとHTTP層の内部retry無効を確認できなければ保留し、外側との掛け算を避ける。
- 次回時刻は指数backoff（上限付き）と有効Retry-Afterの遅い方。現在時刻より前の提案にはしない。次回timeoutまで期限内に収まらなければ保留し、待機を短縮しない。
- runのrequest fingerprint、設定参照、attempt番号/ID・試行ごとのrequest ID・開始/終了時刻を照合。ID再利用、未来時刻、早過ぎる再開始、停止後の試行を拒否。
- `started`のまま結果不明なら、期限経過でも勝手に再開始しない。成功は終了。提案を作る回数は予算消費と混同せず、実際の開始記録だけを数える。
- 技術上限は総試行10・delay24時間・1回timeout1時間。実際の業務/媒体制限の既定値ではない。合成fixture以外の現行設定は未確認。

## 必須の未接続工程

提案から実際に開始するには、最新許可・設定/履歴headを読み直し、単一共有storeへCASで開始を記録してから許可されたreaderを呼ぶ工程が必要。本単位はatomic startや保管を実装しておらず、複数processで実予算を守れたと主張しない。許可根拠・HTTP分類・SDK設定の申告真正性も別検証。

expected run/履歴hashを同じ可変入力から生成しただけでは信頼できる独立保管の代わりにならない。政策・権限の最新版選択や拒否後の人の承認手順を自動化しない。出力は固定reason・次回候補時刻・残予算・参照hashに限り、URLquery、認証値、応答本文を含めない。
