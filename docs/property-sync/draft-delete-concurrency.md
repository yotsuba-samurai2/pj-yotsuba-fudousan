# 下書き削除と同時更新の競合

unit9。旧レビューF-016を現行コードで再確認した。管理APIは読取り時にdraftを確認していたが、DB削除はidだけだったため、確認直後に別の管理者が公開した物件も削除する余地があった。

`deleteProperty(id, expectedUpdatedAt)` を `id + status=draft + updatedAt=確認時の日時` の単一deleteManyへ変更した。件数が1以外の場合は成功とせず、APIは409を返す。公開/成約/編集/別の削除と競合した場合を合成試験で検証した。無条件deleteの呼出しは削除経路からなくした。

既存のbody無しDELETEは維持する。期待日時は今回のサーバー読取りから渡すため、今回防ぐのは読取りから削除までの競合である。ユーザーが昔開いた画面の版との照合までは追加していない。同じupdatedAtのままの下書き編集は検出できず、完全なhash CASや独立revisionへの移行は別の課題。statusがpublished/closedに変わった場合は同じ日時でも削除しない。

新規13試験と既存認可/公開通知25試験、計38試験に合格。独立側でも新規13試験に合格、重大な未解消指摘なし。Prisma境界をmockした検証であり、実DBでの削除・並行transaction試験は行っていない。資格情報・権限・本番データは変更しない。
