# メール候補と共通物件DBの同一性照合

正本は既存Supabase / Prisma `properties`。unit49は物件を作らず、既存のID・募集回・完全な版へ候補を結び付ける読取り専用の部品を追加する。照合結果は常に社内専用・掲載不可である。

## 入力と照合

- 検証済み候補箱からmailboxRef / messageKeyで1件を選び、候補hashを固定する。
- 読取り担当へ明示されたpropertyId / episodeIdだけを要求する。全在庫検索やメールからのID生成は行わない。
- 現在の物件の完全JSONと、独立した募集回・市場区分のmetadataを既存 `fingerprintPropertySnapshot` で検査。更新日時と全内容hashを照合する。各読取り開始より古いsnapshotは現在の再確認に使わない。
- メール、候補hash、正本ID/版に結び付いた手動同一号室確認の根拠を読み取る。確認者・参照・確認日時が欠けるもの、未確認・撤回済みは保留する。
- `registeredRentalIdentity` と `unitKey` を再利用。ただし正本の明示されたsourceの建物/住所/号室が必須で、titleからの推定や住所の前方一致は使わない。区切り文字の衝突も拒否する。
- 候補・正本・確認根拠を最後に再読取りし、編集や撤回を検出する。募集終了済みは再募集の確認待ちとし、自動再公開しない。

## 出力と限界

出力は既存ID/募集回/版、候補・根拠のhash、未確認の数値提案、未完了ゲート。住所・建物名・原文・社内AD情報は含まない。既存writerへそのまま渡せる物件payloadではない。メールの数値が正しいと確定したわけでもない。

readerにはcreate/update/deleteのポートがない。実DB・実媒体・実認証へ接続するadapterは今回追加しない。将来の接続では現在の募集回と権限を信頼できるDB側から解決する必要があり、入力JSONのhashを認証代わりにしない。

読取り完了後の編集はこの部品だけで防げない。実保存時には既存のCAS/receipt処理と最新の権利・条件検査を使う。新規物件の登録はこの照合とは別工程で、該当IDの不在を新規作成へ変換しない。

## 旧取込コードとの区別

調査で `rental-import/candidates.ts` の旧メール採用処理を確認した。unit48開始時の「取込処理なし」はproperty-sync範囲の確認であり、リポジトリ全体では旧処理が存在した。新しい入力受け口と旧処理を区別して扱う。続くunit50で、本人の「受信7日以内・税込報酬総額20万円以上を上書き」に従って旧処理の現行判定も置換する。
