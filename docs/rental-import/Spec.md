# 賃貸物件の自動取込

2026-09-20。対象HPは既存 luck428.com/bukken。専用worktreeで実装。

## 処理
1. 会社Gmailの直近1暦月の受信メールを全ページ取得。件名・本文・添付からAD表記を抽出し、単位・対象部屋・期間を保持。
2. AD2か月以上の候補をITANDI BBとREINS両方のログイン済み画面で同じ号室の現在の在庫掲載を照合。部屋IDで識別し、最新の募集・広告料・いずれかの同一物件資料にある広告可・画像の取得元を記録。画像はユーザーの包括許可を適用。
3. 写真・間取りを取得。一般向け物件情報と業者間情報を分離。未確認情報は補完せず保留。
4. 検証後、既存物件テーブルへ冪等登録。公開モードは設定で指定（初期値draft）。同じ部屋の再実行は重複登録しない。手動編集・募集終了済みは自動上書きしない。
5. 既登録物件も募集を再確認し、終了はclosed。確認できない時は更新日を延ばさない。期限超過した賃貸は公開対象から外す。

## 実行環境
Gmail接続とログイン済みChromeを利用するCodexの定期実行＋既存の管理者認証を使う検証・登録画面 `/admin/bukken/import`。DB接続を設定した環境向けのCLIも用意。非公開APIやブラウザCookieの抽出はしない。取得元の画面変更・認証切れは保留として報告。

## 初期設定
エリア制限なし、1日1回を想定。公開後の掲載終了監視はユーザー追加要件。同一物件のどこか1か所の広告可で掲載可とする。REINS詳細の掲載確認は必須。稼働はコードの本番反映と実データ検証後。全確認先で広告可を確認できない場合は公開しない。

## 検証
ADの全半角・月数・%・曖昧な表記、暦月末、未来日、期限、転載許可、画像不足、二重登録、手動編集保護、内部情報漏洩、認証と公開ゲートを検証。

## 2026-09-20 追加指示の採用ルール
- 広告可：同一住所・建物・号室について、現在確認できる資料のどこか1か所に広告可があれば可。他の取得先の空欄・不可は別途記録する。
- 画像：全画像を転載可とするユーザーの包括指示を根拠に採用。取得元が許諾したという記録に書き換えない。
- 保証会社等：同じ対象・算定基準で入居者負担の厳しい条件の原文を採用。初回と継続費用の大小が逆など一意に比較できない時は未確定。記載のない金額を補完せず、異なるプランを合成しない。
- ペット：資料にある頭数の多い方を採用し、その原文と付帯条件を保持。
- 募集状況：ITANDIとREINSの両方で同一物件・号室の現在の掲載を24時間以内に確認。片方の終了・削除を確認すれば新規掲載しない。既公開物件は直ちに公開を停止し、自動再公開しない。ポータルの広告終了のみでは除外・停止しない。認証切れ・障害・未照合は保留し、古い側の確認から26時間で公開対象外にする。
- 掲載件数：SUUMO・アットホーム・HOME’Sについて候補物件・号室ごとの他社を含む広告件数を確認。広告IDで重複除去し、終了・別号室を除外。店舗数、建物の募集部屋数、検索ヒット数を流用しない。号室未照合は可能性あり、全件未確認は下限値、取得不能は未確認として記録。

- 条件選択後の本文・翻訳は `contentReview` のハッシュ・日時・言語で照合記録を保持。通常の管理APIにも同じ公開条件と自社画像保存、取込物件の識別情報固定を適用する。
- 3ポータルは各24時間以内の確認試行が必須。取得不能は明記できるが、記録の省略・古い記録の使い回しでは更新しない。
