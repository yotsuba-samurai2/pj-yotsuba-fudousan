# 賃貸物件の自動取込

## 先行ゲート（必ず候補化直後に実行）

1. ITANJIの物件詳細で申込数などの数字が表示され、申込済み・申込あり・申込中と判断できる物件は、写真取得・条件比較・REINS照合をせず候補から除外する。数字がない、または申込状態が表示されない物件は除外せず、そのまま次の確認へ進める。
2. 申込済みの数字がない物件は、同一住所・建物・号室で広告可を確認する。送信元ドメインが `ttfuhan.com`（東京建物不動産販売）の受信メールに「広告可」「掲載可」「エンド向け掲載OK」等の明示がある場合は、そのメールを広告可の根拠として採用し、REINS確認を省略する。それ以外はREINSの広告可を確認する。REINSは広告可の確認に限って使用し、賃料・条件・募集状況の採用元にはしない。
3. ITANJI掲載中、AD2ヶ月以上、広告可の根拠（東京建物メールまたはREINS）が揃った物件だけ、写真・間取り取得と詳細条件の検証へ進める。
4. 本番登録前に同一住所・建物・号室の既登録データを照合する。既登録なら新規登録を止め、更新が必要な場合だけ管理画面の「公開済み物件の再確認」から実行する。

## 必須実装指示：Vercel全ページ生成の再発防止

物件データの登録・再確認・掲載終了・画像差替えを契機に、Vercelで公開物件を全件事前生成してはならない。物件詳細の動的ルートは `generateStaticParams` で物件一覧を取得せず、オンデマンド生成とする。全体ビルドはコード変更のデプロイ時に限る。実装レビューでは、ビルドログに公開物件の全件静的生成がないことと、既存のHTTP 404・ISR再検証・IndexNow通知が維持されていることを確認する。

> **運用ルール (2026-09-21改訂):** ITANJI (ITANDI BB) を候補抽出、申込状況、募集状況、賃料、条件の主情報源とする。東京建物不動産販売（`ttfuhan.com`）の受信メールに同一号室の広告掲載可が明示されている場合はメールを広告可の根拠とし、REINS確認を行わない。それ以外はREINSを同一号室の広告可確認に限って使用する。SUUMO・アットホーム・HOME'S・他社HPは条件比較・転載・終了判定に使わない。

担当者照会は `src/lib/rental-import/inquiries.ts` の照会ID、既知宛先照合、重複送信防止、号室照合、返信の自動返信・曖昧回答・矛盾除外を通して記録する。実送信は接続済み会社メールの正式機能に限定し、コードの匿名テストでは送信しない。

2026-09-20。対象HPは既存 luck428.com/bukken。専用worktreeで実装。

## 処理
1. 会社Gmailの直近1暦月の受信メールを全ページ取得。件名・本文・添付からAD表記を抽出し、単位・対象部屋・期間を保持。
2. AD2か月以上の候補をITANJI (ITANDI BB) のログイン済み画面で同じ号室の現在の在庫掲載を照合。部屋IDで識別し、最新の募集・広告料・広告可・画像の取得元を記録。画像はユーザーの包括許可を適用する。
3. 写真・間取りを取得。一般向け物件情報と業者間情報を分離。未確認情報は補完せず保留。
4. 検証後、既存物件テーブルへ冪等登録。公開モードは設定で指定（初期値draft）。同じ部屋の再実行は重複登録しない。手動編集・募集終了済みは自動上書きしない。
5. 既登録物件も募集を再確認し、終了はclosed。確認できない時は更新日を延ばさない。期限超過した賃貸は公開対象から外す。

## 実行環境

> **v1.2の優先:** 下記に残る旧版の複数サイト記述は移行履歴であり、実装・運用では冒頭のv1.2ルールを優先する。物件データ更新でVercelの全ページ生成を行わない。
Gmail接続とログイン済みChromeを利用するCodexの定期実行＋既存の管理者認証を使う検証・登録画面 `/admin/bukken/import`。DB接続を設定した環境向けのCLIも用意。非公開APIやブラウザCookieの抽出はしない。取得元の画面変更・認証切れは保留として報告。

## 初期設定
エリア制限なし、1日1回を想定。公開後の掲載終了監視はユーザー追加要件。同一号室について東京建物メールまたはITANJI・REINSのいずれかで広告可を確認できれば掲載可とする。稼働はコードの本番反映と実データ検証後。広告可を確認できない場合は公開しない。

## 検証
ADの全半角・月数・%・曖昧な表記、暦月末、未来日、期限、転載許可、画像不足、二重登録、手動編集保護、内部情報漏洩、認証と公開ゲートを検証。

## 2026-09-20 追加指示の採用ルール
- 広告可：同一住所・建物・号室について、現在確認できる資料のどこか1か所に広告可があれば可。他の取得先の空欄・不可は別途記録する。
- 画像：全画像を転載可とするユーザーの包括指示を根拠に採用。取得元が許諾したという記録に書き換えない。
- 賃料：ITANJIの原文・円金額・URL・日時を記録し、その値を採用する。REINS・HOME’S・SUUMO等は取得しない。
- 保証会社等：ITANJIの複数プランだけを同じ対象・算定基準で比較し、入居者負担の厳しい条件の原文を採用する。初回と継続費用の大小が逆など一意に比較できない時は担当者へ照会し、記載のない金額を補完しない。
- ペット：ITANJIに複数の頭数条件がある場合は多い方を採用し、その原文と付帯条件を保持。
- 募集状況：ITANJIで同一物件・号室の現在の掲載を24時間以内に確認。終了・削除を確認すれば新規掲載せず、既公開物件は直ちに公開を停止する。認証切れ・障害・未照合は保留し、確認から26時間で公開対象外にする。
- 掲載件数：v1.2では確認しない。過去のポータル件数は公開判定・募集監視に使わない。

- 全公開物件の採用後の本文・翻訳は `contentReview` のハッシュ・日時・言語で照合記録を保持。通常の管理APIにも同じ公開条件と自社画像保存、取込物件の識別情報固定を適用する。
- 3ポータルは各24時間以内の確認試行が必須。取得不能は明記できるが、記録の省略・古い記録の使い回しでは更新しない。

通常編集の更新日時照合とDB比較更新を必須にし、終了から下書き・公開への復帰を拒否する。終了証拠の判定はAD・賃料・広告可・他方の証拠の完全性に依存させない。

2026-09-20追加指示: 保証会社料金・保険料・保証金・短期解約違約金は、指示原文と対象項目をunconfirmedTermsへ保存し「未確認」と明記して公開可。募集・照合・賃料等の検証は緩和しない。
