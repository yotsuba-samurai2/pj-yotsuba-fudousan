## 既存の納品指示に適用する本文確認規則

当日のDaily Columnsの生成済み原稿をGoogleドキュメントへ整理する。原稿を再生成しない。最新mainの `docs/columns-delivery/YYYY-MM-DD.json` と対応Markdownを読み、`todayJst` が対象日に一致することを確認する。runUrl、レビュー処理結果、候補のkeyとfingerprintを確認し、対象日の6本と前日分の保留原稿を混ぜない。

通知とGoogleドキュメント冒頭には、次の事実を別々に記載する。

1. 生成・機械検証が成功した記事数。
2. レビュー処理の成功・失敗・未取得と、判定、blocker・major・minor各指摘数。
3. 今回の候補指紋に対応する公開証跡登録数。
4. 自動公開の品質候補数、品質保留数、公開日待ち数。
5. 未確認一次資料の数と対象、保留の理由。本番公開の実行結果が未照会なら「未照会」と書く。

レビューがpass=trueでもminorがあれば明示する。レビュー失敗、形式不正、候補指紋不一致、欠けた記事証跡は未確認とし、「指摘なし」「未検証なし」と案内しない。アスタリスクで囲んだ未検証マーカーの有無やコミット本文だけから確認済みと推測しない。

品質候補0本なら「生成済みN本、公開証跡0本、品質保留N本。正午公開予定ではありません」と書く。部分承認は品質候補と保留を記事別に記載する。全件が品質候補でも、手動保留・既存DB・公開日・有効期限を公開処理が再判定するため、正午の公開完了を約束しない。`publishedCount: null` は0本の公開実績という意味ではなく未照会である。

日付の一致したreportを取得できない場合は、対象runのレビューJSON、recordログ、hold artifactと現在の候補指紋を直接照合する。どれか欠けた事実は件数不明と記載し、原稿の納品成功と公開承認を分ける。判定できない原稿URLは「予定URL」であり、公開済みURLとは書かない。

前日のPR #480と本日の原稿は番号が重なってもslug・fingerprintが異なる。対象runと正確なkeyで区別する。品質ゲートや手動保留を解除しない。
